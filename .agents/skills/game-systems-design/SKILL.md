# Game Systems Design

## Trigger

Use to turn a fun hypothesis into a decision-rich system, diagnose shallow or
repetitive play, or create controlled alternatives.

## Inputs

Use the concept thesis, pillars, fun hypotheses, reference transformations,
target player, constraints, and available play evidence. Identify the exact
system question before expanding scope.

## Workflow

1. Trace `action -> feedback -> state change -> decision -> consequence ->
   learning` and expose any broken link.
2. Prefer a few interacting rules that create many situations. Treat depth as a
   heuristic involving interaction density, decision consequences, strategic
   horizon, and mastery potential, not feature count.
3. Ask what becomes visible after ten hours that was invisible after ten minutes.
   Adjust the timescale to the game; record when long-term mastery is irrelevant.
4. Design new understanding, not only new content. Seek surprise that is
   retrospectively coherent.
5. Create alternatives by changing one major variable where possible. Include
   subtraction and ablation, not only additions.
6. Parameterize likely mutation points and define observables before coding.
7. Check accessibility versus depth without assuming every game needs maximal
   breadth or replayability.

## Outputs

Produce a system model, decision inventory, parameter list, and variant set.
Route the highest uncertainty to prototype strategy. Use
[systems-heuristics.md](references/systems-heuristics.md) for diagnostics and
anti-patterns.

## Stop Conditions

Stop when one prototype can discriminate among the strongest alternatives.
Return to concept design if mechanics no longer express the intended experience.
