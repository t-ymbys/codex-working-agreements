# Game Concept Design

## Trigger

Use when a project needs a coherent, testable concept rather than more ideas or
features. Do not force one universal recipe for fun.

## Inputs

Use creator intent, taste hypotheses, comparison findings, target player, scope,
platform constraints, and ambition level. Preserve unresolved claims explicitly.

## Workflow

1. State the player fantasy and `The game is fun because ...` using player
   action and consequence, not story, world, polish, or content volume alone.
2. Define two to four pillars that constrain decisions. Add anti-pillars for
   what the game must not become.
3. Map reasons to continue across seconds, minutes, session, hours, campaign,
   and years only where those timescales apply.
4. State `return_reason` and `memory_reason`; for a finite single-play game,
   explicitly allow no replay loop.
5. Test the system without story and the story's contribution to the system.
   Neither needs to stand alone, but their dependency must be intentional.
6. Define a possible signature moment, mechanic, or interaction and answer
   `Why this game, not merely this genre?`
7. Convert the concept into one or more falsifiable fun hypotheses.

## Outputs

Produce a concise concept brief and update `fun-hypotheses.yaml`. Use
[concept-frame.md](references/concept-frame.md) for the brief and coherence
checks.

## Stop Conditions

Stop when the concept constrains design and identifies the next system or
prototype uncertainty. If it remains `competent_but_generic`, return to creative
direction or reference transformation instead of adding features.
